# Oracle Billing Data Lifecycle - Partitioning, Archiving & Benchmarking

**Project 22 - Oracle Database Administration course.**
A telecom operator keeps years of billing records in one table: queries are slow,
maintenance is expensive and data retention is hard to manage. This project designs,
implements and **measures** a data lifecycle strategy for Oracle 19c combining
monthly partitioning, adapted indexing, compression, zero-copy archiving and
metadata purge - compared against the client's current design on the same data.

| | Baseline (current design) | Optimised design (this project) |
|---|---|---|
| Storage | one heap table, all history | monthly interval-range partitions |
| Old data | stays in the table | compressed + read-only (warm), then moved to an archive table |
| Archive | `INSERT ... SELECT` + `DELETE` | 2 x `EXCHANGE PARTITION` (no row copied) |
| Purge | `DELETE` | `DROP PARTITION` |
| Statistics | full table | incremental (new partition only) |

**Web dashboard:** `scripts/07_dashboard.sh` starts a Streamlit page on http://localhost:8501 with the demonstration steps as buttons (tiers, query plans, dry run, incident and recovery, monthly job, security checks, benchmark). `--fresh` reloads the data first (~10 min); `--stop` stops it.

**Technical report (PDF):** [`report/Technical_Report.pdf`](report/Technical_Report.pdf) - LaTeX
sources in `report/` (`report/build.sh`, needs XeLaTeX with the TeX Gyre fonts, e.g. TeX Live or
MacTeX; `--diagrams` re-renders the Mermaid diagrams with a Chromium browser, set `BROWSER` if it
is not Brave on macOS).

Results: [`results/summary.md`](results/summary.md) (generated by the benchmark), interpreted in
[`docs/results_analysis.md`](docs/results_analysis.md); demo rehearsal outputs in `results/demo/`.

## Prerequisites

| Item | Version used | Notes |
|---|---|---|
| Docker Desktop | 29.0 | ~8 GB RAM for the Docker VM |
| Oracle Database container | `oracle/database:19.3.0-ee` (19.19, ARM64) named `oracle19c` | CDB `ORCLCDB`, PDB `ORCLPDB1`, port 1521 |
| Free host disk | >= 10 GB | for the data, checked automatically before loading (`MIN_HOST_FREE_GB`); building the Oracle image needs more (install zip + image) |
| bash, git, curl | any recent | host side; Docker Compose v2 (`docker compose`) |

Python 3.12, python-oracledb 2.5.1, pandas, matplotlib and SQLcl run **inside** the
`tools` container - nothing else is installed on the host.

### The Oracle container

The project uses the course container `oracle19c`. It was built from Oracle's official
Docker build files; the image tag says `19.3.0-ee` because that is the build recipe's
version, while the installed binaries are **19.19 for ARM64** (`LINUX.ARM64_1919000_db_home.zip`).
To recreate it on another machine:

```bash
git clone https://github.com/oracle/docker-images.git
cd docker-images/OracleDatabase/SingleInstance/dockerfiles
# download the 19c install zip from oracle.com (free Oracle account) into 19.3.0/:
#   ARM64 (Apple silicon): LINUX.ARM64_1919000_db_home.zip
#   x86-64:                LINUX.X64_193000_db_home.zip
./buildContainerImage.sh -v 19.3.0 -e
docker run -d --name oracle19c -p 1521:1521 -p 5500:5500 \
  -e ORACLE_SID=ORCLCDB -e ORACLE_PDB=ORCLPDB1 \
  -v oradata:/opt/oracle/oradata oracle/database:19.3.0-ee
docker logs -f oracle19c        # wait for "DATABASE IS READY TO USE!"
```

The scripts need no SYS password: DBA steps use OS authentication inside the container
(`sqlplus / as sysdba`). If `ORCLPDB1` does not reopen after a restart, save its state once:
`alter pluggable database orclpdb1 save state;`. Make the container restart with Docker:
`docker update --restart unless-stopped oracle19c`.

## Quick start

```bash
scripts/init_env.sh          # 1. create .env (random passwords, git-ignored)
scripts/01_setup_db.sh       # 2. tablespaces + users
scripts/02_create_schema.sh  # 3. schema + packages
scripts/03_load_data.sh      # 4. ~24 M rows, 72 months (about 6 min)
scripts/05_benchmark.sh      # 5. benchmark + report -> results/summary.md (~25 min)
```

`04_run_tests.sh` and `05_benchmark.sh` apply the retention policy, so they need a freshly
loaded dataset (the tests only accept the smoke dataset). The demo needs a fresh full dataset
followed by step 0 (see docs/demo.md): after the benchmark, start the dashboard with
`scripts/07_dashboard.sh --fresh`, which does both. To start again:

```bash
scripts/reset.sh --yes && scripts/01_setup_db.sh && scripts/02_create_schema.sh && scripts/03_load_data.sh
```

(`02_create_schema.sh` cannot run twice on the same schema without a reset.)
On Linux hosts, files written by the tools container in `results/` belong to root
(`sudo chown -R $USER results` if needed).

Smaller dataset (functional checks in ~1 minute). Run it in a sub-shell so that
`ENV_FILE` does not leak into later full-size commands:

```bash
(umask 077; sed -e 's/^ROWS_PER_MONTH=.*/ROWS_PER_MONTH=3000/' -e 's/^CUSTOMERS=.*/CUSTOMERS=5000/' .env > .env.smoke)
( export ENV_FILE=$PWD/.env.smoke
  scripts/reset.sh --yes && scripts/01_setup_db.sh && scripts/02_create_schema.sh \
    && scripts/03_load_data.sh && scripts/04_run_tests.sh )
```

## Configuration

`.env` (see `.env.example`): connection settings, account passwords and dataset parameters.
`ROWS_PER_MONTH` and `CUSTOMERS` (scale) can be changed freely. The calendar
(`DATA_START_MONTH=2020-11`, `DATA_MONTHS=72`, `AS_OF_MONTH=2026-11`) is what the automated
tests, the benchmark workload and the demo scripts are written for; both the tests and the
benchmark refuse to run with another calendar. `ENV_FILE=<file>` selects another env file
for the scripts and the tools container (e.g. the smoke dataset).

Retention policy (table `DLM_CONFIG`, changeable without redeploying code):

| Parameter | Default | Meaning |
|---|---:|---|
| `HOT_MONTHS` | 12 | months kept uncompressed and read/write |
| `ONLINE_MONTHS` | 36 | months kept in `BILLING_RECORDS` |
| `RETENTION_MONTHS` | 60 | legal retention; older data is purged |
| `MIN_RETENTION_MONTHS` | 60 | safety floor, purge refuses anything shorter |
| `AS_OF_MONTH` | 2026-11 | reference "today" (reproducible runs) |

## Running the lifecycle

```sql
-- as TELCO_OWNER
-- show what would happen
exec dlm_pkg.run_lifecycle(p_dry_run => true)
-- purge, warm, archive, statistics, validation of frozen months
exec dlm_pkg.run_lifecycle

select * from dlm_job_log order by log_id desc fetch first 20 rows only;
select dlm_pkg.validate_integrity('BILLING_ALL', p_to_month => date '2025-11-01') months_in_error from dual;
```

Single operations: `dlm_pkg.warm_partition(date '2024-01-01')`,
`dlm_pkg.archive_partition(...)`, `dlm_pkg.purge_partition(...)`.
Integrity of frozen months: `select dlm_pkg.validate_integrity('BILLING_ALL', p_to_month => date '2025-11-01') from dual;`
(without an upper bound, HOT months that the application changed since loading are reported too).

## Tests

`scripts/04_run_tests.sh` runs 43 automated functional tests (dry run, guards, simulated
crash and recovery, interrupted warm, system-named partitions, idempotence, read-only
protection, application write window, live HOT writes, `p_as_of`, integrity) plus 25
asserted security checks for `TELCO_APP` and `TELCO_ANALYST`;
it exits non-zero if any check fails. The outputs in `results/tests/`
come from the smoke dataset (the tests are destructive; the full dataset is kept for the
benchmark).
